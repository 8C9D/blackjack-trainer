### How this ships

Two independent channels, neither of which is a server:

1. **Web: a static site on GitHub Pages.** `.github/workflows/pages.yml` builds with `--base-href /blackjack-trainer/`, assembles `site/` from `dist/blackjack-trainer/browser/` plus the two legal pages plus a copy of the shell as `404.html`, and deploys via `actions/deploy-pages@v4` to `https://8c9d.github.io/blackjack-trainer/`.
2. **iOS: an App Store binary.** A paid iPhone app, `MARKETING_VERSION 1.0`, bundle id `com.arthurzhang.blackjacktrainer.app`, signed with `DEVELOPMENT_TEAM C3W798H8U8` (`ios/project.yml:20`). Submission is manual and owner-driven (`LAUNCH-CHECKLIST.md`).

There is no container, no server binary, and no published library.

### What "production" means here, and who breaks

Derived from `README.md`, `.github/workflows/pages.yml`, `LAUNCH-CHECKLIST.md` and `ios/AppStore/*.html`:

- **The user who breaks is a trainee**, and the thing they lose is practice history - streaks, accuracy, weak spots - held only in `localStorage` (web) or `UserDefaults`/iCloud KVS (iOS). There is no server copy and no account. `src/app/core/services/storage.ts:44-52` says this in the source itself.
- **The second party who breaks is the owner**, a single developer shipping a paid App Store binary and a public GitHub Pages site under their own name. A false published privacy statement or a broken store URL lands on them personally.
- There is no wagering, no money, no PII, no telemetry, and no third party receiving anything. That materially lowers the ceiling on how bad any defect here can be, and the severities below reflect that.

## ASSUMPTIONS

1. **The working tree counted as clean.** `git status --porcelain` showed exactly two untracked directories, `.agents/` and `.codex/`, containing only agent skill definitions and a Codex config - no application code. `git diff` and `git diff --cached` were both empty. I read "uncommitted changes" as modified or staged **tracked** files and continued. Mitigation: no commit in this run uses `git add -A`; every commit names its paths, so those directories cannot be swept in.
2. **The tool sandbox was disabled for every build/test command.** The first sandboxed `npm run build` died with exit 134 (SIGABRT) and no diagnostic. Recorded in `reviews/BASELINE.md`.
3. **The Pages path is `/blackjack-trainer/`**, taken from `.github/workflows/pages.yml:37` and the URL in `ios/AppStore/support.html:45`. I could not confirm the site is actually live (that would require a network fetch to a non-local host).
4. **"Production" covers both artifacts.** The prompt says "this repository"; the repository ships a web app and an iOS app, so both were swept.
5. **The iOS iCloud capability is unprovisioned**, per `LAUNCH-CHECKLIST.md:22-23` and `TRIM-REPORT.md:70`. This is an out-of-repo portal setting I cannot verify. It is load-bearing for finding I1's severity and for the NOT-DEFECTS ruling on the privacy text; if it is wrong, both change.
6. **`public/manifest.webmanifest` is an application asset, not deploy configuration**, so editing it does not violate the prohibition on changing deploy config. It ships inside the bundle and is served to the browser; the deploy configuration is `pages.yml`, which I have not touched.

## NOT DEFECTS

- **`tools/serve-dist.mjs:33-34`'s path-traversal claim is true.** The comment asserts `normalize()` prevents escaping `ROOT`. Verified by execution: `/%2e%2e/%2e%2e/%2e%2e/package.json` → 404, and `--path-as-is /../../package.json` → 404. `new URL(...).pathname` always begins with `/`, and `normalize` collapses leading `..` on an absolute path. No finding.
- **The App Store privacy text is accurate as shipped.** `ios/AppStore/privacy.html:48-50` and `support.html:45` say "This version of the app does not sync", while `AppModel.swift:49` does construct a real `UbiquitousKeyValueStore`. With the capability unprovisioned (assumption 5), `NSUbiquitousKeyValueStore` behaves as a local store and no data leaves the device, so the statement holds. Recorded because the statement's truth depends on an out-of-repo portal setting rather than on anything in this tree - a coupling worth knowing about, but not a code defect.
- **`ios/project.yml:20` `DEVELOPMENT_TEAM: C3W798H8U8` is not a secret.** An Apple Team ID is public in every distributed binary's provisioning profile and grants nothing on its own.
- **`ios/BlackjackTrainer/App/AppModel.swift:102` `preconditionFailure` on bundled-data load failure** is a deliberate fail-loud on a build-integrity invariant that CI gates (`ios/BlackjackTrainerTests`, plus the parity fixture check). Crashing on a corrupt build beats running with silently wrong strategy charts in a trainer whose entire value is being right.
- **`BackupService.restore` on a valid but empty backup wipes local data** (`src/app/core/services/backup.service.ts:78-124`). That is the documented semantic - a restore is the state the backup captured, not a merge - and `build()` legitimately produces `data: {}` on a fresh browser. Correct as written.
- **The double filter on backup keys is defence in depth, not a bug.** `parseBackup` admits any `blackjack-`-prefixed key (`backup.model.ts:97-103`) while `replaceNamespace` writes only declared `BACKUP_KEYS` (`backup.service.ts:129-134`). The wider parse and the narrower write are both intentional.
- **Drill timers do not leak.** All three `setTimeout` owners register `DestroyRef.onDestroy(() => this.clearAdvance())`: `basic-strategy-drill-page.component.ts:275`, `deviations-drill-page.component.ts:316`, `card-counting-page.component.ts:439`.

## CANNOT ASSESS

- **Whether the declared-but-unprovisioned iCloud entitlement (`ios/BlackjackTrainer/BlackjackTrainer.entitlements`) blocks archive/export signing.** Determining this requires Apple's developer portal and notarisation services - non-local resources this run may not contact. Worth flagging: `.github/workflows/ios-ci.yml` builds only for the **simulator**, which does not sign, so no gate in this repository exercises the signed device build at all. Fixing that would be a CI change, which this run may only report.
- **Real iCloud multi-device behaviour** (finding I1). Requires two provisioned devices and Apple's servers.
- **Whether the GitHub Pages site is live and serving** the layout `pages.yml` describes. Requires a network fetch to a non-local host.
- **Cross-browser behaviour of `URL.revokeObjectURL` immediately after `anchor.click()`** in `src/app/core/services/backup.service.ts:70-74`. It works in Chromium (`e2e/smoke/backup.e2e.ts` passes against the real build), and Chromium is the only browser configured in `playwright.config.ts`. Whether Firefox or Safari cancel the download when the object URL is revoked in the same task is not something this repository's tooling can determine, so no finding is asserted either way.
